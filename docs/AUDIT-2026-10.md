# Design System Audit — October 2026

An assessment of The Membrane Palette at v2.0.0, what v2.1.0 changed in response, and what is still open. Severity: **High** = a user-facing defect or a gap that blocks adoption; **Medium** = drift or friction that will become a defect; **Low** = polish.

The short version: v2.0 had a strong token pipeline (DTCG source, OKLCH, `light-dark()`, a contrast gate) and almost nothing on top of it. Components existed only as prose, every consumer had to rebuild them, and the copies had already drifted. v2.1 adds a 25-component CSS library, and the token pipeline's discipline (single source, generated output, build-time checks) now covers components and their docs too.

---

## 1. Components

| # | Finding | Severity | v2.1 response |
|---|---|---|---|
| 1.1 | No component library. §6 of the spec described 8 components as prose recipes ("Padding: 0.875rem 2rem…"); consumers had to translate each into CSS by hand. | High | 25 components shipped as CSS in `components/`, bundled into `membrane-components.css` and `membrane.css`. |
| 1.2 | The only implementation (showcase-local CSS) had already drifted from the recipes: different button padding, font size, weight, secondary background and hover behavior. | High | Recipes retired; the showcase is built from the library, so there is one implementation. |
| 1.3 | Missing everyday components: field/label/error, checkbox, radio, switch, select, textarea, alert, badge, avatar, table, tabs, accordion, dialog, tooltip, breadcrumb, progress, layout primitives. | High | All added. |
| 1.4 | Button hover used `filter: brightness()`, which also brightened the label and can lower its contrast. | Medium | Explicit `-hover` tokens; the gate verifies label contrast on the hover fill. |
| 1.5 | Clickable-card pattern unspecified (risk of wrapping a whole card in `<a>`, which makes the full card text the link name). | Medium | `.mp-card__link` stretched-link pattern with focus ring on the card. |
| 1.6 | No convention for variants or states, so every consumer would invent their own (`.btn--outline`, `.is-active`…). | Medium | One API: `mp-` class, `data-*` options with closed value sets, state via ARIA/native attributes. |

## 2. Accessibility

| # | Finding | Severity | v2.1 response |
|---|---|---|---|
| 2.1 | Inputs used `--color-border-default` as their only boundary: ≈1.3:1 on cream, failing WCAG 1.4.11 (needs 3:1). | High | `--color-border-input` (gated ≥3:1 on page, card and dialog surfaces) used by every form control. |
| 2.2 | Showcase input removed its focus outline (`outline: none`) and relied on a 15%-alpha glow. | High | Every component keeps the 2px `--focus-ring`; inset where a scroll container would clip it. |
| 2.3 | `--code-comment` was 3.7:1 on `--code-bg`; code colors weren't in the gate. | High | Lightened to 5.2:1; all six code colors gated. |
| 2.4 | Spec'd tag recipe (terracotta text on `--color-terracotta-10`) was never contrast-checked. | Medium | Register pairs `--color-human-text`/`-bg`, `--color-digital-text`/`-bg`, gated. |
| 2.5 | The gate measured status/register washes over the page only. axe-core run against the new showcase found 4 failures when the same washes sit on cards (where the wash composites differently). | High | Gate extended to check every wash over card surfaces too; four text values adjusted. axe now reports 0 violations on the showcase and starter page in both modes. |
| 2.6 | Touch-target rule cited WCAG 2.5.5 as if it were AA (it's AAA; 2.5.8 AA is 24px), and the small button size had no touch-screen fallback. | Low | Citation corrected; `data-size="sm"` grows to 44px under `pointer: coarse`. |
| 2.7 | Custom-drawn controls would lose their checked state in Windows High Contrast. | Medium | Checkbox, radio, switch and select revert to native rendering under `forced-colors: active`. |
| 2.8 | Theme script ran at the end of `<body>` (flash of wrong theme) and forced light mode on first visit instead of following the OS. No skip link. | Low | Theme applied in `<head>`, OS-following by default; skip link added. |

## 3. Tokens

| # | Finding | Severity | v2.1 response |
|---|---|---|---|
| 3.1 | No surfaces for overlays (dialog/popover), inverse (tooltip), or neutral hover/pressed states. | Medium | `--color-bg-elevated` (lighter in dark mode), `--color-bg-inverse`/`--color-text-inverse`, `--color-bg-hover`/`--color-bg-active`. |
| 3.2 | Status colors had fill and text variants but no background wash, so alerts would reach for primitives. | Medium | `--color-{success,warning,error,info}-bg` + `--color-info-text`. |
| 3.3 | `ease-in-out` required by §8.1 rule 3 but no token existed; 65ch measure required by §3.5 but no token. | Low | `--ease-in-out`, `--measure`. |
| 3.4 | No control-height scale; buttons and inputs derived height from padding. | Low | `--size-control-sm/md/lg`. |
| 3.5 | Two names for the same size (`--text-sm` = `--text-small`, etc.) make generated code inconsistent. | Low | Aliases deprecated (kept until v3.0.0). |
| 3.6 | The gate couldn't evaluate `color-mix()` values, so any mixed token was unverifiable. | Medium | New `mix` token type, resolved in oklab by the build (verified to match Chromium's computed value). |

## 4. Documentation & drift

| # | Finding | Severity | v2.1 response |
|---|---|---|---|
| 4.1 | Spec tables were hand-maintained and stale: §2.2 listed rgba literals for tokens that are now `color-mix()`, §13.1 hand-typed ratios, §15 described `--color-tint-*` tokens that never existed. | Medium | §2.3 and §13.1 tables are generated; stale text corrected. |
| 4.2 | Showcase dark-mode demo duplicated dark hex values by hand instead of using the theme mechanism it was demonstrating. | Low | Real `data-theme` subtrees (`.mp-surface`). |
| 4.3 | CI only checked the two token CSS files for freshness; the showcase's generated regions could go stale. | Medium | CI fails on any uncommitted change after `build:system`. |

## 5. Agent-readiness

| # | Finding | Severity | v2.1 response |
|---|---|---|---|
| 5.1 | An agent had only prose to work from: no list of valid classes, variants or states, so it would invent plausible-looking ones. | High | `components/manifest.json`: classes, allowed `data-*` values, styled states, knobs, tokens and examples per component. |
| 5.2 | No entry point for LLMs. | Medium | `llms.txt` (+ `llms-full.txt` on the site) with the house rules. |
| 5.3 | Nothing stopped docs from describing APIs that don't exist. | High | Docs lint: README examples may only use classes/attributes/values the CSS implements. The API section of each README and the manifest are derived from the CSS. |
| 5.4 | No copyable full-page example. | Medium | `examples/starter.html`. |

---

## Still open (recommended next steps)

1. **Tag a release** (`v2.1.0`) and document pinned CDN URLs. Every jsDelivr link currently tracks the default branch, so a breaking change ships to every consumer instantly.
2. **Automate what was verified by hand for this release.** axe-core and the behavior checks (tabs keys, dialog, tooltip Escape, skip link) were run locally with Playwright; adding them to CI would make them permanent. Visual regression was previously ruled out as disproportionate — with a component gallery to snapshot, it is now worth reconsidering.
3. **Components that need real scripting:** menu/dropdown, combobox, toast, pagination. They need focus management that CSS can't provide; they should come with `membrane.js` behavior and the same docs lint.
4. **Icons.** §7.3 recommends Phosphor or Lucide but nothing ships; components accept inline SVG. Decide on one set and document the sizes against `--size-icon-*`.
5. **Fonts.** Still loaded from Google Fonts; self-hosting with `font-display: swap` and metric-matched fallbacks would remove a third-party dependency and layout shift.
6. **Framework wrappers** (React/Vue/web components) are deliberately not included. The `data-*` + ARIA API maps 1:1 to props if they're ever wanted; generate them from `manifest.json` rather than hand-writing them.
7. **Remove the deprecated `--text-sm/base/md/lg/xl` aliases in v3.0.0**, with a migration note.
